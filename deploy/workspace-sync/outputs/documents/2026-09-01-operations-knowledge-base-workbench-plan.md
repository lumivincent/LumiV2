# Lumiterra V2 运营知识库工作台规划

- 规划日期：2026-09-01
- 当前阶段：产品与交互规划
- 适用范围：Lumiterra V2 运营、Marketing、增长、社区、经济机制、竞品与行业案例研究

## 1. 目标

知识库要解决的不是“资料放在哪里”，而是四个连续问题：

1. 零散信息出现时，能否低成本地先保存下来；
2. 整理后，能否清楚区分原始证据、外部观点、内部判断和待确认假设；
3. 形成观点后，能否从观点反向追到具体来源、片段和历史版本；
4. 做分析、策略或内容时，能否只调用相关且状态合适的信息，并留下本次实际使用的版本记录。

目标流程：

```text
随手捕获 → 待整理收件箱 → 来源与证据 → 观点卡 → 主题页
                                      ↓
                               运营实验 / 上下文包
                                      ↓
                            分析、内容、活动与决策
                                      ↓
                                  使用记录
```

## 2. 范围与边界

### 2.0 工作台界限

知识库只是在现有应用中增加一个独立的一级入口，不改造、不占用也不搬移现有“文档与分析”“内容创作”“素材工作室”的页面与数据。

- 知识库使用独立的 `knowledge/` 文件目录和 `knowledge-*` metadata；
- 现有内容、素材、产品来源和项目记忆不自动复制到知识库；
- 知识库资料不自动注入现有创作流程；只有用户主动选择上下文包或明确要求调用时才建立引用；
- 建立引用时只保存关系和使用快照，不改变原文件状态或归属；
- 知识库故障、收件箱积压或资料未整理，不影响现有工作台的使用。

### 2.1 知识库的范围

知识库不局限于 Olympus DAO，后续可以承载：

- 竞品、协议、游戏与社区案例；
- Marketing、增长、获客、留存和传播机制；
- Token、经济机制、激励设计与风险案例；
- 用户洞察、市场信号和行业变化；
- Lumiterra 可参考的做法、不可照搬的条件和待验证假设；
- 从研究中形成的观点、建议、实验和复盘。

Olympus DAO 作为第一个试点主题，用来验证整套收集、整理、追溯和调用流程。

### 2.2 与现有信息体系的边界

| 区域 | 回答的问题 | 是否可以作为 Lumiterra 产品事实 |
|---|---|---:|
| `sources/` | Lumiterra 当前产品是什么 | 是，仍需注意文档版本 |
| `memory/` | 当前阶段、已确认工作方式与持久决策 | 是，但只记录内部已确认事项 |
| 运营知识库 | 外部世界发生了什么、我们如何理解、可能怎样应用 | 否，除非另有当前产品来源支持 |
| `outputs/` | 某次分析、策略、内容或资产的正式产出 | 否，产出中的产品主张仍需回查 `sources/` |
| 内容长期记忆 | Lumiterra 已定稿或已发布内容过去怎样表达 | 只代表历史表达，不自动代表当前事实 |

外部研究资料不能进入 `sources/`。知识库中的“可借鉴”也不能自动变成产品设计、Marketing 承诺或 Token 收益预期。

## 3. 核心信息对象

第一版建立六种人工可见对象和一种系统记录，避免把来源、讨论和结论混在一起。

### 3.1 来源卡 Source

来源卡保存“我们看到了什么”，是追溯链的起点。链接、粘贴文本、上传文件、截图、视频时间点和会议记录都先成为来源卡。

必需字段：

- 稳定 ID，例如 `SRC-20260901-001`；
- 标题、来源类型、URL 或本地文件路径；
- 作者或发布方、发布日期、捕获时间；
- 为什么保存这条资料的一句话；
- 所属主题、标签和语言；
- 来源等级：官方/一手、研究与数据、可信二手、社区内容、未知；
- 核验状态：未核验、单一来源、交叉支持、存在冲突；
- 时效性：长期有效、阶段性、快速变化；
- 内容摘要、允许保存的短摘录或本地快照引用；
- 原始内容哈希与版本号。

来源工作流只使用三个状态：`待整理`、`已整理`、`已归档`。真实性判断放在独立的核验状态中，避免把“已经看过”误解成“已经证实”。

### 3.2 证据单元 Evidence Unit

证据单元是来源卡内可单独引用的片段，不单独占一个主导航入口。每条包括：

- Evidence ID；
- 对该片段的准确转述；
- 原文位置：页码、段落、图表、时间戳或 URL 锚点；
- 证据性质：数据、直接陈述、作者观点、推断、个案或传闻；
- 短摘录或截图引用；
- 核验状态。

观点卡应尽量关联到具体 Evidence ID，而不是只关联整篇文章。

### 3.3 讨论记录 Discussion

讨论记录保存“我们这次讨论了什么”。日常与 Codex 进行的资料搜集、分析、脑暴和观点推演，只要属于知识工作，就在一次讨论结束或形成阶段结论时沉淀一条结构化记录。

主要字段：

- 稳定 ID，例如 `DSC-20260901-001`；
- 日期、讨论主题和原始问题；
- 关联 Codex 任务或会话 ID；
- 本次使用的来源、附件和已有知识；
- 形成的阶段结论；
- 发散想法和不同方向；
- 仍需验证的假设与开放问题；
- 从本次讨论提炼出的观点卡；
- 创建者、更新时间和版本。

默认保存结构化讨论纪要，而不是无差别复制整段聊天。需要完整语境时，可以保留原会话引用或明确保存完整转录。讨论记录本身只代表讨论历史，不是外部证据，也不是已经采纳的结论。

脑暴中形成的结论进入观点卡时，若没有外部或内部证据，应标记为“待确认假设”或低信心观点，不能进入默认公开内容上下文。

### 3.4 观点卡 Insight

观点卡保存“我们如何理解”，一张卡只表达一个可以讨论或验证的判断。

主要字段：

- 稳定 ID，例如 `INS-20260901-001`；
- 一句话结论；
- 类型：观察、运营解释、建议、风险判断、待确认假设；
- 论证说明；
- 支持证据、反向证据与冲突资料；
- 对 Lumiterra 的潜在适用方式；
- 成立条件、不可迁移条件和主要风险；
- 信心：低、中、高；
- 状态：草拟、已复核、已采纳、已否决、已替代；
- 版本、替代关系和修改原因；
- 被哪些分析、内容、实验或决策使用过。

“已采纳”只表示已被运营采用为当前工作判断，不表示它成为产品事实。

### 3.5 主题页 Topic

主题页是持续更新的研究入口，例如“Olympus DAO：早期增长与崩盘教训”。它不复制全部资料，而是聚合：

- 范围与研究问题；
- 时间线、关键实体和术语；
- 相关来源和观点卡；
- 相关讨论及其阶段结论；
- 当前形成的结论与反对意见；
- 仍缺少的证据；
- 对 Lumiterra 的可借鉴、不可照搬和待验证事项；
- 最近更新及观点变化。

主题页是活的索引；历史结论通过观点卡版本保留，不在主题页里手工复制多份。

### 3.6 运营实验 Experiment

案例研究不能直接等同于执行。需要真正尝试的建议转成运营实验：

- 假设与目标人群；
- 来源观点卡；
- 执行动作、成功指标和风险护栏；
- 前提假设与停止条件；
- 结果、复盘和最终决定。

状态为：提议、进行中、已完成、已停止。

### 3.7 上下文包 Context Pack 与使用快照 Usage Snapshot

上下文包是一次任务真正要调用的知识集合，可以临时创建，也可以保存为可复用模板。它包含：

- 本次目标与问题；
- 选中的主题、来源、证据和观点版本；
- 当前 Lumiterra 产品来源版本；
- 反向证据、风险提醒与明确排除项；
- 允许用于事实、只允许用于启发、仍需确认的边界。

当分析或内容生成真正开始时，系统冻结一份使用快照，记录精确 ID、版本、内容哈希和时间。以后即使观点被修改，也能还原当时为什么得出该产出。

## 4. 零散信息的进入方式

### 4.1 顶部快速捕获

知识库页面顶部固定一个捕获栏，接受：

- URL；
- 直接粘贴的文字；
- 文件或图片；
- 一句临时想法；
- URL 加一句“为什么值得看”。

保存时只强制要求内容本身，其他字段均可稍后补充。系统立即生成来源卡或临时笔记，进入“待整理”，保证记录动作足够轻。

### 4.2 日常讨论沉淀

日常讨论采用“先讨论、后结构化沉淀”的方式，不要求为了记录而打断对话：

1. 讨论开始时可选择已有主题，也可以直接开始并暂时进入“未分类”；
2. 讨论过程中引用的链接、文件和旧观点随会话关联；
3. 出现阶段结论或本次讨论结束时，生成一条讨论记录；
4. 将其中值得长期复用的单一判断提炼为观点卡；
5. 将仍需调查的部分转成研究问题，将明确要尝试的部分转成运营实验；
6. 讨论记录永久保留当时语境，后续观点变化通过新版本或替代关系表达。

资料搜集型讨论侧重来源与证据，脑暴型讨论侧重发散想法、假设和分歧。两者都进入知识库，但不会被赋予相同的可靠性。

### 4.3 自动补全但不自动下结论

系统可以自动完成：

- 标题、作者、发布方、发布时间和语言识别；
- Canonical URL、内容哈希和重复资料提示；
- 候选主题、标签和别名；
- 摘要与候选证据片段；
- 同一 URL 出现新内容时提示建立新版本。

系统不能在无人确认时自动把摘要升级为已复核观点，也不能把外部资料写入 Lumiterra 产品事实。

### 4.4 防止收件箱变成垃圾堆

收件箱显示三种清理信号：

- 未设置主题；
- 未判断来源等级或核验状态；
- 长时间没有处理。

整理一条资料时只需完成“放入主题、判断来源、保留证据、创建或关联观点”四步。暂时无价值的资料归档，不要求删除。

## 5. 工作台信息架构

主导航新增“知识库”，内部采用五个入口：

1. **总览**：快速捕获、待整理数量、近期主题、最近观点和需要复核的内容；
2. **收件箱**：处理所有零散输入，支持批量设置主题、标签和归档；
3. **主题与讨论**：从研究问题进入讨论、来源、观点、时间线和缺口；
4. **观点**：按状态、信心、适用领域和证据完整度查看；
5. **实验与调用**：运营实验、上下文包以及历史使用记录。

“来源”不必占用主入口：全局搜索可以筛选全部来源，主题页和观点页也能打开来源详情。

### 5.1 详情页的追溯体验

来源详情需要显示：

- 原始信息和版本；
- 证据单元；
- 从它形成的观点；
- 它被用到过的上下文包与产出。

观点详情需要显示：

- 当前结论和状态；
- 支持证据与反向证据；
- 对 Lumiterra 的适用条件；
- 历史版本和替代原因；
- 被哪些实验、内容、文档或决策使用。

任何正式观点都应在两次点击内到达原始来源位置。

## 6. 搜索与调用设计

### 6.1 第一版搜索

第一版先做好可解释的关键词、全文和字段搜索，不急于引入向量数据库。支持组合筛选：

- 对象类型；
- 主题与标签；
- 状态；
- 来源等级与核验状态；
- 时间范围和时效性；
- 观点类型、信心与是否有反向证据；
- 是否被使用过。

增加术语别名表，例如 `Olympus / Olympus DAO / OHM`、`POL / Protocol Owned Liquidity`。搜索结果明确显示为什么命中。

### 6.2 之后再增加语义检索

数据量明显增加后，再增加语义相似度。语义结果只能帮助召回，最终排序还要综合：

- 与任务的直接相关度；
- 观点状态；
- 来源质量和核验状态；
- 时效性；
- 是否存在未解决的冲突。

### 6.3 与现有工作区的调用关系

- **文档与分析**：可调用已整理来源、草拟观点和冲突资料，但产出必须标明各自状态；
- **内容创作**：默认只推荐“已复核/已采纳”的观点，并同时读取当前 `sources/` 产品事实；
- **素材工作室**：不默认注入知识，仅在用户主动关联主题或上下文包时使用；
- **项目记忆**：只接收经过团队确认且具有持续效力的内部决定；
- **知识库**：不把内容草稿、模型回答或某次临时想法自动当作可靠知识。

内容或分析页面应提供“添加知识”入口，允许用户查看推荐项、手动选择、排除某项，并在执行前预览最终上下文包。

## 7. 版本、冲突与删除规则

### 7.1 不覆盖证据历史

- 原始快照一旦保存不直接改写；
- 同一来源更新后创建新版本，并保留旧哈希；
- 来源元数据纠错需要有修改时间和原因；
- 观点发生实质变化时建立新版本，通过 `supersedes` 关联旧版本；
- 旧观点标记“已替代”而不是消失。

### 7.2 冲突是信息，不是异常

两条来源冲突时同时保留，并在观点卡显示：

- 冲突发生在哪个具体判断；
- 各自来源等级、时间和适用范围；
- 当前采用哪一种解释以及原因；
- 是否仍需团队确认。

### 7.3 默认软归档

普通操作只允许归档。真正删除仅用于重复上传、隐私或合规要求，并且需要明确确认。归档内容不参与默认调用，但仍可追溯历史使用。

## 8. 建议的本地存储结构

沿用当前“Markdown 正文 + JSON metadata”的方式，便于人工读取、Git/文件级追溯和工作台检索。

```text
knowledge/
  sources/             # 来源卡与证据单元
  discussions/         # 日常讨论的结构化记录
  insights/            # 观点卡及其版本
  topics/              # 主题页
  experiments/         # 运营实验与复盘
  context-packs/       # 可复用上下文包
  attachments/         # 允许本地保存的附件
snapshots/
  knowledge/           # 来源版本快照
data/
  knowledge-metadata.json
  knowledge-usage.json
  knowledge-aliases.json
```

文件在状态变化时不移动，避免路径变化使历史引用失效。工作流状态只写入 metadata。

公共 metadata 至少包含：

```text
id, type, path, title, status, topicIds, tags,
createdAt, updatedAt, version, contentHash,
relatedIds, supersedesId, archivedAt
```

正式文档和内容的 metadata 增加：

```text
knowledgeContextId, knowledgeUsageSnapshotId
```

## 9. Olympus DAO 首个试点主题

首个主题页暂定为“Olympus DAO：早期增长与崩盘教训”，但现在不预填未经调研的结论。研究结构可以先包括：

- 关键阶段与时间线；
- 发行、质押、Bond 与 Protocol Owned Liquidity 的机制事实；
- 早期叙事、社区符号、传播渠道和获客路径；
- 增长飞轮成立所依赖的市场条件；
- 用户结构、资本行为和关键指标变化；
- 高 APY、稀释、反身性、流动性和信任风险；
- 做得好的部分、失败部分和争议观点；
- 哪些经验可转译成 Lumiterra 的游戏、Agent、社区与经济叙事；
- 哪些做法应设为禁区；
- 需要产品或经济团队进一步确认的问题。

最终输出不是一篇孤立报告，而是一组可复用来源卡、证据单元、观点卡和一个持续更新的主题页。

## 10. 开发顺序

### 阶段 A｜结构、捕获与追溯

- 建立目录、metadata schema 和稳定 ID；
- 新增知识库主导航、总览、收件箱和主题页；
- 支持 URL、文字与文件快速捕获；
- 支持将一次日常讨论保存为结构化讨论记录；
- 支持来源卡、证据单元、主题、标签、状态和归档；
- 完成关键词/全文搜索、组合筛选、重复 URL 和哈希提示；
- 完成来源版本与历史记录。

阶段 A 完成后，零散信息已经可以安全进入系统并被找回。

### 阶段 B｜观点、冲突与调用

- 增加观点卡、反向证据、信心和替代关系；
- 增加主题聚合和研究缺口；
- 增加上下文包、预览和冻结的使用快照；
- 将知识选择器接入文档分析和内容创作；
- 在产出详情显示“使用了哪些知识及版本”。

阶段 B 完成后，知识才能可靠地参与日常运营任务。

### 阶段 C｜实验与智能辅助

- 增加运营实验和复盘；
- 增加自动摘要、证据候选、标签候选和矛盾提示；
- 增加需要复核、过期风险和来源更新提醒；
- 数据量足够后再增加语义检索；
- 根据实际使用记录优化推荐排序。

## 11. 第一版验收标准

1. 粘贴一个链接或一段文字即可立即保存，其他字段可以稍后补齐；
2. 每条观点都能看到支持证据、反向证据、信心和状态；
3. 从正式观点到原始来源位置不超过两次点击；
4. 搜索 `OHM` 能通过别名找到 Olympus 主题、相关来源和观点；
5. 未整理资料不会被默认注入内容创作；
6. 内容创作不能把外部研究误当成 Lumiterra 产品事实；
7. 每次调用都能还原当时使用的知识 ID、版本和产品来源哈希；
8. 来源更新或观点被替代后，历史产出仍保留原来的使用快照；
9. 归档内容不会出现在默认推荐中，但历史引用仍然有效；
10. Olympus 试点能完整走通“捕获—证据—观点—主题—上下文包—产出—追溯”。
11. 保存知识讨论不会新增、移动或修改 `outputs/twitter/`、`outputs/assets/` 和既有内容 metadata；
12. 一次资料搜集或脑暴讨论可以独立沉淀为讨论记录，并把结论、假设和开放问题分开。

## 12. 当前已确认与仍需确认

### 已确认

- 知识库的长期范围不局限于 Olympus DAO；
- 它需要支持零散、发散、随时出现的信息；
- 清晰记录、方便追溯和能够被运营任务调用是核心目标；
- Olympus DAO 适合作为首个调研与流程验证主题。
- 知识库作为独立一级入口存在，不占用或改造现有内容、分析与素材工作区；
- 日常资料搜集、分析和脑暴讨论都需要能够沉淀为知识库讨论记录。

### 本规划给出的运营/产品建议

- 使用“来源—证据—观点—主题—实验/上下文包—使用快照”的对象模型；
- 第一版坚持 Markdown 正文与 JSON metadata，不立即引入复杂数据库；
- 先做可解释的字段与全文搜索，数据量扩大后再增加语义检索；
- 未整理资料和未复核观点不进入内容创作的默认上下文。

### 开发前仍需团队确认

- 是否接受上述五个内部入口名称与信息层级；
- 第一阶段是否需要直接抓取网页正文，还是先保存链接、人工粘贴内容和上传文件；
- 哪些成员可以把观点从“已复核”升级为“已采纳”；
- 附件、网页快照与外部内容的保存期限和合规边界；
- 第一版是否同时接入内容创作，还是先独立完成知识库内部闭环。
